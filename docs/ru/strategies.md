# 🎯 Ценовые стратегии — дизайн-спецификация

> Источник истины по фиче «динамический подбор цены экспериментом».

## Проблема
Floor при заданной марже (напр. 30%) задирает цену части позиций так высоко, что это останавливает продажи. Нужно подбирать цену по фактическим продажам, а не держать статичную РРЦ.

## Подход (обоснование — `docs/` исследование, методология)
Строгий A/B при низком объёме (λ=0.3–5 шт/день) статистически невозможен (нужны сотни продаж на цену). Поэтому:
**within-SKU ladder (ступенчатый поиск) + Gamma-Poisson байес + event-based стоп + гистерезис.**
- Держим цену до **N_min≈12 продаж ИЛИ T_max** (окно анализа), потом решаем.
- Решение — по **апостериорной ожидаемой метрике** (Gamma-Poisson), берём нижний перцентиль (p25) → риск-аверсия к малым выборкам.
- Шаг крупный (±7–10%, coarse-to-fine до ±3–5%), гистерезис δ≥5%, откат после 2 плохих замеров.
- Коридор — узкое окно вокруг рабочей цены, **floor — жёсткий низ** (кроме `liquidation`).
- λ<0.3/день → в эксперимент НЕ берём (нет сигнала).

## Стратегии (`products.strategy_type`)
| Тип | Цель | Оптимум |
|---|---|---|
| `ref_price` (дефолт) | держим РРЦ, без эксперимента | — |
| `max_profit` | максимум `(цена − себест − комиссия(цена)) × штуки` | внутренний |
| `max_revenue` («макс продажи») | максимум `цена × штуки` (выручка) | внутренний (эластичность≈1) |
| `max_units` | максимум штук при марже ≥ заданной | стремится к floor с целевой маржой |
| `liquidation` («слив») | слить FBO-остатки по мин. цене | вниз, **допустим минус ниже себестоимости** |

### Стратегия `liquidation` — особый режим
- Пользователь **вручную** указывает SKU + **допустимый минус** (на сколько ниже себестоимости можно).
- Обходит floor (единственная стратегия, которой это разрешено) в пределах допустимого минуса.
- 🔴 **КРИТИЧНО:** дни слива помечаются `is_dirty=1` + `liquidation_flag=1` в `sales_daily`, ведётся история слива. Движок и будущий ЛЛМ **обязаны** исключать эти дни из оценки спроса — иначе всплеск от слива будет ошибочно принят за реакцию на цену.

## Окна анализа
Выбираемые: **14 / 30 / 60 дней** (на товар или магазин). Влияет на расчёт λ и метрик.

## Безопасность
- **Gate:** первые N циклов — dry-run (движок ПРЕДЛАГАЕТ цену, нужен ручной апрув), затем авто-применение.
- **Kill-switch:** три уровня — глобальный / на магазин / на SKU. Мгновенно останавливает эксперимент и откатывает к `ref_price`/последней безопасной цене.
- **Floor-гард:** ни одна цена (кроме liquidation) не ниже floor.
- **Пилот:** авто-выбор топ-N (~20) SKU по объёму продаж + ручное добавление.
- **Заморозка рычагов:** на пилотных SKU не менять акции/рекламу (один рычаг — цена).

## Конфаундеры → `is_dirty_flag` (день не использовать для вывода о цене)
Стокаут, промо-день, всплеск рекламы/буста, сдвиг СПП (WB), слив. Считаем спрос только по «чистым» дням.

## Данные: `sales_daily` (append-only, 1 строка на SKU×день)
Гранулярность дня обязательна (агрегаты убивают развязку конфаундеров). Это и движок, и датасет под ЛЛМ.
Поля: `store_id, product_id, offer_id, marketplace, date, units, revenue, profit, price_seller, price_buyer_est, cost_unit, commission_pct, floor, ceiling, promo_flag, promo_price, ad_spend, boost_pct, stock_qty, in_stock_flag, spp_pct(WB,null), comp_price(null), experiment_id, step_idx, is_dirty_flag, liquidation_flag, posterior_lambda_mean, posterior_lambda_p25`.

## Источники продаж по площадкам
- **Ozon:** `/v1/analytics/data` (metrics: ordered_units/revenue; dimension: sku, day).
- **WB:** `nm-report` (заказы/выкупы по nmID/день). ⚠️ считать по **выкупам**, не заказам (возвраты).
- **Яндекс:** расширить `fetchOrdersEconomics` (уже есть, 7 дн → окно).
⚠️ Наблюдаемый спрос реагирует на **цену-для-покупателя** (WB: ×(1−СПП); Ozon: marketing_price; YM: буст), а двигаем мы цену продавца. Логируем обе цены раздельно.

## Валидация движка (Монте-Карло)
Симуляция `scripts/simStrategy.cjs` на синтетическом пуассон-спросе, разрыв по ЗНАЧЕНИЮ метрики vs теор. оптимум:
- **max_profit: ~2%**, **max_units: ~2%** — отлично.
- **max_revenue: ~12%** — приемлемо: оптимум выручки пологий + фундаментальный шум низкого объёма (единичный замер на цену обманывается ±2σ-драйвами). Митигация: ручной gate, накопление данных во времени (апостериор уплотняется), порог λ.
Движок: фаза первичного скана коридора (бракетит оптимум) → ladder-уточнение; слабый приор + минимум дней наблюдения (иначе низкоценовые точки недооценены).

## Что реализовано
- **Схема данных:** `sales_daily`, `experiments`, `strategy_log`, поля стратегий в `products`, kill-switch.
- **Сбор продаж** по трём площадкам с backfill и суточной задачей: `salesCollector.cjs` + фетчеры.
- **Движок:** `lib/bayesPoisson.cjs` (гамма-пуассон, квантиль Wilson–Hilferty, обратная нормальная по Acklam) + `lib/strategyEngine.cjs` (скан коридора, ladder, гистерезис, целевые функции, фильтр «грязных» дней). Чистая математика без сети и БД — поэтому тестируется и симулируется.
- **Оркестрация:** `strategyRunner.cjs` — юнит-экономика, карантин-кап WB, gate `auto_apply`, kill-switch на магазин и глобальный.
- **Наблюдаемость:** `strategy_log` с решением по каждому SKU каждого прогона, панель `/strategies`.
- **Тесты:** юнит-тесты движка и байесовской части, детерминированный тест сходимости ladder, свойства безопасности (потолок коридора, граница слива, floor > 0, недостижимая маржа в `max_units`), Монте-Карло симуляция.

## Запуск пилота (когда накопится история)
1. `/strategies` → магазин → «Выбрать пилот» (топ-N по продажам) ИЛИ назначить вручную.
2. Несколько дней движок копит чистые дни и пишет лог-предложения (dry-run, цены НЕ меняются).
3. Ревью лога → если предложения разумны → кнопка «Авто» на товар = живое применение (floor — жёсткий низ).
4. Контроль: kill-switch магазин/глобально мгновенно останавливает.

## План развития (будущее, вне v1)
ЛЛМ-агент рекомендаций (схема уже готова под него); мониторинг цен конкурентов; реклама/буст как **рычаг** (сейчас только сбор); **анализ влияния промо на продажи** (собираем флаги, в логику не закладываем); пулинг низкообъёмных SKU (иерархический байес).
