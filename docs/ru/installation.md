# Установка

Путь от `git clone` до первого работающего магазина. Каждый шаг сверен с кодом.

> Это приложение меняет **реальные цены в реальных магазинах**. Пройдите разделы «Первые шаги» и «Проверка перед боем» до того, как включите репрайсер на боевом аккаунте.

---

## 1. Что понадобится

- **Node.js 20 или новее.** В `package.json` объявлено `"engines": { "node": ">=20" }`, в `.nvmrc` — `20`.
- **Инструменты сборки нативных модулей.** `better-sqlite3` компилируется при установке (node-gyp), поэтому нужны `python3`, `make` и `g++`:

| Система | Что поставить |
|---|---|
| macOS | `xcode-select --install` (Command Line Tools; Python 3 идёт в комплекте) |
| Debian / Ubuntu | `sudo apt install build-essential python3` |
| Alpine | `apk add python3 py3-setuptools make g++` |

  На Python 3.12 может потребоваться **`py3-setuptools` / `python3-setuptools`**: из 3.12 убрали `distutils`, который старый node-gyp всё ещё импортирует, а вендоренная копия из setuptools возвращает его на место. В `Dockerfile` этот пакет ставится явно по той же причине.

- Ничего больше: базы данных, брокера очередей и внешнего кэша проект не требует. Всё состояние — один файл SQLite.

---

## 2. Установка зависимостей

```bash
git clone <адрес-вашего-форка> && cd public_repricer
npm ci
```

`npm ci` вместо `npm install` — чтобы версии совпали с `package-lock.json`. На этом шаге собирается `better-sqlite3`; если сборка падает — см. раздел «Диагностика».

## 3. Файл `.env`

```bash
cp .env.example .env
```

**Обязательных переменных всего две.**

### `BETTER_AUTH_SECRET`

Ключ, которым подписываются сессионные куки. Сгенерируйте:

```bash
openssl rand -hex 32
```

Поведение при отсутствии (`auth.mjs`): при `NODE_ENV=production` процесс **бросает исключение и не стартует**; в остальных случаях выводится предупреждение и приложение работает с неподписанными сессиями — для локальной разработки это допустимо, для чего-либо ещё нет.

### `BETTER_AUTH_URL`

Публичный базовый адрес приложения — ровно тот, который вы открываете в браузере. По умолчанию `http://localhost:3001`.

**Если он не совпадает с реальным адресом, вход молча не работает.** Симптом характерный: форма логина принимает пароль, не показывает ошибку, а после перезагрузки страницы вы снова не авторизованы. Причина в том, что better-auth выставляет куку для `baseURL`, и браузер её не принимает и не отправляет обратно. Из этого следуют два практических правила:

- в проде адрес должен быть `https://…` — только по HTTPS кука помечается `Secure`;
- если вы ходите на приложение по внешнему домену, `BETTER_AUTH_URL` — это домен, а не `http://localhost:3001` и не IP.

Та же переменная по умолчанию задаёт CORS-allowlist: `TRUSTED_ORIGINS` заполняется из неё, если не задана явно. Значение `*` недопустимо — вместе с `credentials: true` это открыло бы сессионную куку любому сайту.

### Остальные переменные (все со значениями по умолчанию)

| Переменная | Назначение |
|---|---|
| `PORT` | порт API, по умолчанию `3001` |
| `NODE_ENV` | `development` / `production` |
| `DB_PATH` | файл SQLite, по умолчанию `./ozon.db`; создаётся сам |
| `UPLOAD_DIR` | каталог для загруженных прайс-листов |
| `TRUSTED_ORIGINS` | CSV разрешённых Origin, по умолчанию — `BETTER_AUTH_URL` |
| `FORCE_PUBLIC_DNS` | `1` — все DNS-запросы процесса через 8.8.8.8 / 1.1.1.1 |
| `EXTERNAL_API_KEY` | Bearer-ключ внешнего API. **Пусто = внешний API выключен** (`503`) |
| `EXTERNAL_API_ALLOWED_IPS` | CSV разрешённых IP; пусто = принимаются любые |
| `EXTERNAL_API_RATE_PER_MIN` | лимит запросов в минуту на IP, по умолчанию `120` |
| `S3_*`, `BACKUP_RETAIN`, `BACKUP_HOUR` | ежедневный бэкап в S3-совместимое хранилище; пустой `S3_ENDPOINT` = выключено |
| `SENTRY_DSN_BACKEND`, `VITE_SENTRY_DSN` | Sentry; пусто = выключено |
| `VITE_API_TARGET` | только для разработки: куда dev-сервер Vite проксирует `/api` |

## 4. Миграций запускать не нужно

**Команды миграции в проекте нет.** Ни `npm run migrate`, ни каталога с файлами миграций, ни таблицы версий схемы.

Схема создаётся и обновляется **автоматически при старте процесса**: модуль `db/connection.cjs` при загрузке вызывает `initSchema()` (все `CREATE TABLE IF NOT EXISTS` и индексы) и `runMigrations()` (идемпотентные `ALTER TABLE … ADD COLUMN`, ошибка «duplicate column name» глотается). Таблицы авторизации создаёт сам better-auth в том же файле БД при импорте `auth.mjs`.

Практически это значит:

- первый запуск на пустом каталоге просто создаёт `ozon.db` — никаких подготовительных шагов;
- обновление версии приложения не требует ручных действий с базой: достаточно перезапустить процесс;
- откатить миграцию средствами приложения нельзя — единственный путь назад это резервная копия файла БД.

Подробности — в [Архитектуре](architecture.md), раздел «Подход к миграциям».

## 5. Первый администратор

Регистрации в интерфейсе нет: на странице входа только форма входа, а новых пользователей заводит администратор (`Настройки → Пользователи`, через админ-плагин better-auth). Поэтому самый первый аккаунт создаётся из командной строки:

```bash
ADMIN_PASSWORD='ваш-надёжный-пароль' npm run seed
```

Что делает `seed-admin.mjs`:

- **требует `ADMIN_PASSWORD` длиной не менее 12 символов** — иначе печатает подсказку и выходит с кодом 1. Пароля по умолчанию нет намеренно: этот аккаунт может менять цены во всех подключённых магазинах;
- берёт `ADMIN_EMAIL` (по умолчанию `admin@example.com`) и `ADMIN_NAME` (по умолчанию `Admin`);
- создаёт пользователя через better-auth и затем прямым SQL проставляет ему `role = 'admin'`;
- повторный запуск на существующем пользователе безопасен: печатает «Admin user already exists, skipping».

Переменные можно положить и в `.env` — скрипт читает их оттуда же, откуда и приложение.

## 6. Запуск в режиме разработки

```bash
npm run dev:all
```

Это `concurrently` из двух процессов:

- `npm run server` → `node server.cjs`, API и планировщик на **:3001**;
- `npm run dev` → Vite, интерфейс на **:5173**.

Открывать нужно **:5173**. Dev-сервер Vite проксирует `/api` на бэкенд — цель задаётся `VITE_API_TARGET` (по умолчанию `http://localhost:3001`). Меняйте её, если API поднят на другом порту или на другой машине.

Процессы можно запускать и раздельно, в двух терминалах:

```bash
npm run server   # только API + планировщик
npm run dev      # только UI
```

Полезно знать: **планировщик стартует вместе с API**, а не отдельно. Как только `npm run server` поднялся и в базе есть магазин с включённым репрайсером, начинается работа с площадкой. На незнакомой базе первый запуск лучше делать с выключенным репрайсером.

Сборка прода: `npm run build` (`tsc -b && vite build`) кладёт статику в `dist/`, откуда её раздаёт сам Express — в проде отдельный веб-сервер для фронтенда не нужен.

## 7. Docker

Для локального стенда достаточно двух команд:

```bash
cp .env.example .env      # заполните BETTER_AUTH_SECRET
docker compose up --build
```

Что в образе: multi-stage сборка (`node:20-alpine`), фронтенд собирается в первом стейдже, во втором остаются только прод-зависимости; данные лежат в именованных томах `repricer_data` (`/app/data/repricer.db`) и `repricer_uploads`. Порт публикуется как `${PORT_PUBLISHED:-3001}:3001`. `stop_grace_period: 30s` согласован с graceful shutdown в коде (принудительный выход через 25 с).

Для продакшена используйте overlay:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
```

Overlay требует явно заданный `BETTER_AUTH_URL` (`:?set the public https:// URL`) и переключает Sentry в `production`.

**TLS обязателен.** Контейнер слушает обычный HTTP и не терминирует TLS сам. Ставьте перед ним обратный прокси (nginx, Caddy, Traefik), а `BETTER_AUTH_URL` задавайте с `https://` — только тогда сессионная кука помечается `Secure`. Публиковать порт 3001 в интернет напрямую нельзя.

Если резолвер хоста не достаёт до API площадок, в `docker-compose.prod.yml` есть закомментированный блок `dns: 8.8.8.8 / 1.1.1.1`, а в приложении — переменная `FORCE_PUBLIC_DNS=1`.

## 8. Подключение магазина

Магазины добавляются в интерфейсе: **Настройки → Добавить новый магазин**. Первым делом выбирается платформа — от неё зависит набор полей (`src/components/settings/StoreForm.tsx`).

Общие для всех площадок поля: название магазина, интервал обновлений (10 минут / 1 час / 6 часов / 24 часа), настройки репрайсера (интервал, пороги отклонений), налоговая ставка `tax_rate` и минимальная маржа `min_margin_percent`, флаги работы с акциями.

### Ozon

| Поле | Где взять |
|---|---|
| **Client ID** | личный кабинет продавца Ozon → **Настройки → API-ключи** |
| **API Key** | там же, при создании ключа Seller API |

Ключ нужен с доступом к методам товаров и цен: репрайсер читает `/v5/product/info/prices` (цены, комиссии, логистика, эквайринг) и пишет `/v1/product/import/prices`, а монитор дополнительно ходит за видимостью и акциями.

Отдельный флажок «Антибан» (`antiban_enabled`) есть только у Ozon — он замедляет обход каталога: размер батча падает со 100 до 50 товаров, а пауза между батчами растёт с 500 мс до 3 с.

### Wildberries

| Поле | Где взять |
|---|---|
| **API-токен WB** | личный кабинет продавца → **Настройки → Доступ к API** |

Токен один, но у него должны быть отмечены **четыре категории доступа**. В подписи поля формы и в комментарии к колонке `wb_api_key` в `db/connection.cjs` перечислены одни и те же:

- **Контент** — карточки товаров (`content-api`): `nmID`, `vendorCode`, категория `subjectID`, габариты (из них считается объём для логистики);
- **Цены и скидки** — чтение и запись пары `price`/`discount` и список ценового карантина (`discounts-prices-api`);
- **Аналитика** — остатки на складах WB (асинхронный отчёт `warehouse_remains`) и отчёты (`seller-analytics-api`);
- **Продвижение** — работа с акциями (`dp-calendar-api`).

Токен вставляется целиком; клиент принимает его как в виде `<token>`, так и `Bearer <token>`.

Важно про идентификаторы: у WB в `products.ozon_id` хранится **nmID**, а в `offer_id` — **vendorCode**. Ваш прайс-лист должен быть в терминах `vendorCode`.

### Яндекс.Маркет

| Поле | Где взять |
|---|---|
| **Business ID** | кабинет продавца: идентификатор кабинета (бизнеса) |
| **Campaign ID** | идентификатор магазина/кампании внутри кабинета |
| **Api-Key (OAuth-токен)** | кабинет → раздел API Партнёрского API |

Все три обязательны: у Яндекса доступ привязан к кампании, а не к продавцу, поэтому и вызовы обновления цен идут с `campaignId`, а не с парой «client_id + ключ», как у Ozon.

Дополнительно у магазинов Яндекса есть свои настройки: `ym_boost_cap_percent` (потолок буст-буфера, по умолчанию 30 %), `ym_floor_max_raise_percent` (максимальный шаг роста цены за прогон, 20 %) и `ym_promo_exit_enabled`.

### Ozon Performance API (реклама) — отдельно

Реклама Ozon живёт на другом хосте и с **другими учётными данными**: `client_id` и `client_secret` создаются в **рекламном кабинете → Настройки → API-ключи** и не совпадают с ключами Seller API. В форме магазина их полей нет — они кладутся в `app_settings` под ключом `perf_api_<store_id>`:

```bash
node -e "require('./db/strategies.cjs').setAppSetting('perf_api_<store_id>', JSON.stringify({client_id:'...',client_secret:'...'}))"
```

После этого работает CLI-инструмент управления рекламой:

```bash
node scripts/adsCut.cjs <store_id> --list              # только список кампаний
node scripts/adsCut.cjs <store_id>                     # dry-run: план, ничего не меняется
node scripts/adsCut.cjs <store_id> --apply --factor=0.5 # применить: срезать бюджеты вдвое
```

Хост — `api-performance.ozon.ru` (старый `performance.ozon.ru` не используется), токен `client_credentials` живёт 30 минут и кэшируется в памяти процесса.

## 9. Первые шаги после подключения

### 9.1. Синхронизация

Нажмите синхронизацию у магазина (или дождитесь автоматического запуска — планировщик проверяет `update_interval_minutes` каждую минуту). Синк вычитывает товары, текущие цены, остатки и статусы в локальную базу. Пока синк не прошёл, ничего дальше делать нельзя: репрайсер сопоставляет позиции по `offer_id` из базы.

### 9.2. Эталонные цены и себестоимость

Скачайте шаблон Excel (**Настройки → импорт цен → шаблон**): сервер соберёт его из текущего каталога магазина. Колонки шаблона и подписи из кода:

| Колонка | Обязательность |
|---|---|
| `Артикул` | не изменять |
| `Название` | справочно |
| `Цена сейчас` | справочно, не импортируется |
| `Цена` | **обязательно** — эталонная цена, до неё репрайсер восстановит цену при падении |
| `Старая цена` | необязательно |
| `Мин. цена` | необязательно |
| `Себестоимость` | необязательно, но см. ниже — репрайсер не поставит цену ниже |

Парсер терпим к форматированию: `"1 300,50"` (в том числе с неразрывным и тонким пробелом) читается как `1300.5`; колонки ищутся регулярными выражениями, так что подойдут и `offer_id` / `price` / `cost`.

При загрузке есть два режима: сохранить только эталон (`ref-only`) — цены на площадку не уходят — и полный импорт. Для **Wildberries полный импорт всё равно не шлёт цены**: он записывает только эталон и себестоимость, а на площадку цены отправляет репрайсер, потому что прямой пуш сломал бы пару `price`/`discount` и мог бы уронить товар в ценовой карантин.

### 9.3. Что репрайсер не тронет

Два условия, о которых спрашивают чаще всего:

- **Без `ref_price` товар вообще не рассматривается.** Репрайсер строит рабочий список только из позиций с заполненной эталонной ценой; если эталонов нет ни у одной, прогон завершается предупреждением `Нет эталонных цен в БД. Загрузите цены через импорт Excel.`
- **Без `cost_price` не считается floor** — безубыточная нижняя граница. Товар при этом останется в работе (цена будет восстанавливаться до эталона), но **защита «не продать ниже себестоимости» для него не действует**. Более того, внешний API при действующей политике `policy_require_floor` отклонит запись цены на такой SKU с кодом `no_floor`.

Дополнительно репрайсер пропускает: товары в акции (`skipped_promo`), в карантине (`skipped_quarantine`), позиции, где эталон ниже себестоимости (`skipped_below_cost` — почти всегда это опечатка в Excel), SKU в режиме `disposal` и товары, которые ведёт движок стратегий (`in_experiment`).

Для Ozon есть ещё одна тонкость: floor считается только при `tax_rate > 0`. Если налоговая ставка магазина оставлена нулевой, расчёт безубыточной цены для Ozon не выполняется вовсе. У Wildberries и Яндекса нулевая ставка трактуется как «0 %», и защита продолжает работать.

## 10. Проверка перед боем

Прежде чем включать репрайсер на боевом магазине, пройдите этот список.

**1. Dry-run.** Он есть на нескольких уровнях:

- **Внешний API:** у `POST /api/ext/v1/stores/:id/prices` параметр `dry_run` по умолчанию **`true`** — забытое поле не должно двигать реальные цены. В ответ приходит `preview` с тем, что было бы отправлено.
- **Импорт цен:** сначала `preview` (разбор файла и таблица предпросмотра в интерфейсе), и только потом сохранение; режим `ref-only` пишет эталон, ничего не отправляя на площадку.
- **Реклама:** `node scripts/adsCut.cjs <store_id>` без `--apply` печатает план.
- **Floor Яндекса:** `node scripts/ymFloorDryCheck.cjs "<имя магазина>"` — read-only: считает floor на реальных данных и печатает таблицу, ничего не записывая.

**2. Kill-switch.** Есть три независимых выключателя:

| Уровень | Как выключить |
|---|---|
| Репрайсер магазина | снять `repricer_enabled` в настройках магазина |
| Ценовые стратегии, один магазин | `POST /api/stores/:id/strategy/kill-switch` (или `POST /api/ext/v1/stores/:id/kill-switch`) — все эксперименты магазина останавливаются, цены возвращаются к эталону |
| Ценовые стратегии, глобально | `POST /api/strategy/kill-switch` (или `POST /api/ext/v1/kill-switch/global`) — флаг в `app_settings` |
| Внешний API целиком | убрать `EXTERNAL_API_KEY` (тогда `503 not_configured`) или выключить рантайм-флаг `external_api_enabled` в `app_settings` (`503 disabled`) |

**3. Откат по снапшоту.** Перед каждой массовой операцией система сама делает снимок текущих цен затронутых позиций в `price_snapshots`. Посмотреть и откатить:

```
GET  /api/stores/:id/snapshots
GET  /api/stores/:id/snapshots/:snapshotId
POST /api/stores/:id/snapshots/:snapshotId/rollback
```

В интерфейсе это раздел истории снапшотов у товаров. Откат отправляет на площадку цены из снимка — то есть это такая же запись цен, со всеми ограничениями площадки.

**4. Проверка применения.** Через 3 минуты после отправки цен верификатор перечитывает их с площадки и ставит `VERIFIED_OK` / `VERIFIED_FAIL` (допуск 1 %). После первой боевой отправки загляните в список `pending` — это самый быстрый способ убедиться, что площадка действительно приняла цены, а не ответила формальным «200».

**5. Резервная копия.** Если настроены `S3_*`, база выгружается ежедневно в `BACKUP_HOUR` (по умолчанию 03:00), хранится `BACKUP_RETAIN` копий. Без S3 просто скопируйте файл `DB_PATH` (вместе с `-wal` и `-shm`) при остановленном процессе.

## 11. Диагностика

### Не собирается `better-sqlite3`

Симптом: `npm ci` падает на node-gyp, в логе — `gyp ERR!`, `Python not found` или `ModuleNotFoundError: No module named 'distutils'`.

- Поставьте инструменты сборки из §1.
- На Python 3.12 доставьте `setuptools` (`python3-setuptools` / `py3-setuptools`) — он возвращает удалённый `distutils`.
- Проверьте версию Node: на 18 и старше сборка может не пройти, требуется 20+.
- Смена мажорной версии Node требует пересборки: `rm -rf node_modules && npm ci`.

### Вход не работает, ошибок нет

Почти всегда это `BETTER_AUTH_URL`. Он должен быть **ровно тем адресом, который открыт в браузере** — со схемой, доменом и портом. Проверьте:

- за обратным прокси — это внешний `https://`-адрес, а не `http://localhost:3001`;
- в браузере после входа появилась ли кука сессии;
- если фронтенд открыт с другого адреса (например, Vite на `:5173` смотрит на API другой машины) — добавьте адрес в `TRUSTED_ORIGINS` через запятую, иначе CORS отклонит запрос с `Origin not allowed`;
- в проде без `BETTER_AUTH_SECRET` процесс вообще не стартует — посмотрите первые строки лога.

### Не резолвятся домены API площадок

Симптомы: в `api_logs` ошибки без HTTP-статуса с кодами `EAI_AGAIN`, `ENOTFOUND`, `ENODATA`. Типичный виновник — внутренний DNS-прокси Docker (`127.0.0.11`), который непоследовательно резолвит домены Ozon и Яндекса.

Решение — `FORCE_PUBLIC_DNS=1`: процесс переводит все запросы на 8.8.8.8 / 1.1.1.1. Переменная выключена по умолчанию, потому что меняет резолвинг для всего процесса. Альтернатива на уровне контейнера — раскомментировать блок `dns:` в `docker-compose.prod.yml`.

Отдельный случай — Яндекс: там уже встроен принудительный IPv4-резолвинг (`dns.resolve4` с пятью повторами по 200 мс), потому что `dns.lookup` на некоторых хостах возвращал только IPv6, а `ENODATA` у Яндекса бывает транзиентным.

### `429` от Wildberries

WB применяет строгий лимит на продавца целиком. В клиенте уже стоит **глобальная на процесс** очередь: минимум 1200 мс между любыми запросами к WB (≈5 запросов за 6 секунд), плюс до 3 ретраев с паузой из заголовка `X-Ratelimit-Retry` или экспоненциальным откатом.

Если `429` всё равно много:

- проверьте, не ходит ли **другой** ваш инструмент тем же токеном — троттлинг работает только внутри этого процесса;
- убедитесь, что не запущено два экземпляра приложения на одной базе (это в любом случае недопустимо, см. [Архитектуру](architecture.md));
- увеличьте интервалы синка и репрайсера у магазина — реже прогоны, меньше запросов.

### Другое

- **`503 not_configured` на `/api/ext/v1/*`** — не задан `EXTERNAL_API_KEY`. `503 disabled` — выключен рантайм-флаг `external_api_enabled`.
- **`409 context_stale` при записи цен** — контекст изменился; перечитайте `GET /context` (свежий контекст приходит прямо в теле ошибки) и повторите. Это штатное поведение, см. [Внешний API](api-external.md).
- **Репрайсер «ничего не делает»** — посмотрите итог прогона в логах: строка `REPRICER_SUMMARY` содержит разбивку по всем причинам (`ok`, `corrected`, `skipped_promo`, `skipped_quarantine`, `skipped_below_cost`, `skipped_no_price`, `fetch_errors`), и каждая позиция попадает ровно в одну категорию.
- **Ozon вернул 200, а цена не изменилась** — ищите в `api_logs` запись с текстом `items rejected by Ozon`: отказы по отдельным позициям приходят внутри успешного ответа и разбираются отдельно.
