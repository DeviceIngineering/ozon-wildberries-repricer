# 价格是如何决定的

本文回答的是「程序为什么给出了这个价格」。它写给运营店铺的人，而不是读代码的人。实验引擎的技术说明见 [strategies.md](strategies.md)，系统的整体构造见 [architecture.md](architecture.md)。

---

## 概览

价格由四个数字决定。其中三个由你设定，第四个由系统自己算出来。

| 数字 | 谁来设定 | 含义 |
|---|---|---|
| **成本价**（`cost_price`） | 你 | 这件商品让你花了多少钱。没有它，保护就不起作用——程序没有依据去算亏损 |
| **基准价**（`ref_price`，即建议零售价） | 你 | 需要守住的价格。平台把价格挪走时，调价器会把它拉回来 |
| **区间边界** | 你，可选 | 价格实验的下限和上限 |
| **保本价下限**（`floor_min_price`） | **系统** | 计算出来的保本点：低于这个价格，商品就是亏本卖 |

有一条始终生效的规则：**保本价下限压过基准价**。如果你设的基准价低于下限，程序不会亏本销售——它会在驾驶舱里生成一条「基准价低于成本」的任务，并跳过这个商品。

## 保本价下限：这个数字是怎么来的

下限就是把平台扣走的一切都算进去、再加上你的目标毛利率之后仍能保本的价格。它**按平台分别计算**，因为各家的经济账本就不同。这不是抠细节：一套通用公式套所有平台，误差能有几十个百分点。

### Ozon

```
下限 = (成本价 × (1 + 毛利率%) / (1 − 税率%) + 物流费 + 收单费) / (1 − 佣金%)
```

佣金、物流和收单费不是拍脑袋定的——它们取自 Ozon 针对每个商品返回的实时数据，因此会随类目和仓库一起变。这里的税是嵌套的：它按扣费之后剩下的部分计算。

### Yandex Market

这里的税按**毛收入**计——按买家支付的全部金额，而不是扣完之后的余额。这不是小事：以前那套和 Ozon 共用的公式会把下限算低，实实在在造成过亏损。

除此之外，分母里还要算上**实际的 boost 费率**。Yandex 在任何费率接口里都不返回它，因此它是从最近 7 天的订单统计里反推出来的：只取那些确实被推广过、且样本量足够的商品。这个费率受店铺设置里的上限约束。

如果所有按比例扣费加起来逼近 95%，程序会认定数据异常而不设下限——宁可不动价格，也不要因为算错而把价格抬上去。

### Wildberries

```
按商品类目的 FBO 佣金 + 按箱体体积的物流费
+ 退货物流费 × 未签收比例
```

还有一处细节：**税率等于零表示零税率，而不是「未设定」**。如果你适用的是专利税制或自雇者税制，保护照常工作。以前在 Ozon 上遇到这种情况，下限会被悄悄关掉——这个问题已经修好了。

## 决策顺序

调价器的每个运行批次，对每个商品都走这道阶梯。第一个命中的条件即为最终结论。

1. **商品处于「清运」模式（`disposal`）** → 价格冻结，不碰。
2. **商品在价格实验中** → 价格由策略引擎决定，调价器不插手。
3. **没有成本价** → 也就没有下限。商品会以「未填写成本价」进入驾驶舱。此时基准价照常守住，但没有亏损保护。
4. **基准价低于成本价** → 跳过并上报。这是数据有错，不是亏本销售的理由。
5. **商品在促销活动中** → 活动里的价格没法用常规机制抬上去。如果促销价低于成本价，就生成一条驾驶舱任务；若开启了自动退出，商品会被撤出活动。
6. **商品处于价格隔离**（Wildberries） → 平台不会应用价格，等待卖家后台里的确认。
7. **价格低于下限** → 抬到下限。
8. **价格偏离基准价**超过阈值 → 拉回基准价。
9. 否则 → 什么也不做，日志记 `ok`。

偏离阈值（下跌和上涨分别设置）在店铺设置里配置。用意是不要为了几分钱的差异去折腾价格。

## 促销活动是怎么处理的

平台会自己把商品塞进折扣，这是毛利被悄悄吃掉的头号来源。程序在三个层面上应对：

- **自主禁止。** 在 Ozon 上会设置一个开关，禁止平台自动把商品加进活动。这是治因，不是治果。
- **白名单。** 你勾选想参加的活动，其余的一律把商品撤出来。
- **折扣深度上限。** 即便是允许参加的活动，也不得把价格压到设定的百分比之下。

退出依据的是平台上的实时活动列表，而不是可能已经过期的本地副本。已冻结的活动会跳过。如果一轮没能全部删干净，剩下的由下一个运行批次补上。

Wildberries 没有「退出活动」这个接口，所以退出是通过 Prices API 恢复「基础价 + 折扣」这一组合来实现的。

## 主价格：一个价格覆盖三个平台

如果同一个货号在多个平台上销售，设定一个买家看到的价格显然比设三个方便。主价格会把它展开成各平台自己的规则：

- **Ozon** —— `price`、`old_price` 和 `min_price`，并满足平台约束：最低价不低于售价的 50%，划线价高于售价且不小于两倍最低价。
- **Wildberries** —— 「基础价 + 折扣」的组合，因为那里没法直接设定买家价。程序会反推折扣，使最终价格正好落在你要的数上。
- **Yandex Market** —— `price` 加 `discountBase`，而且折扣必须落在允许的 5–99% 区间内，否则 Market 会把划线价删掉。

下发之前一律先给出「现在 → 将变成」的预览，并标出被跳过的商品及其原因。下发按店铺打成一个批次，以免撞上限流；下发之前会留一份快照供回滚。

## 什么时候用实验来定价

上面讲的都是规则：「守住基准价」「不要低于下限」。但正确的基准价本身是未知的。价格实验就是依据真实销量把它找出来的办法。

它**不对所有商品开启**，只对你选中的那些，并且默认工作在建议模式：引擎在日志里写下它会把价格定成多少、为什么这么定，但在你对某个具体商品打开「自动」之前，什么都不会真的改。

它是这样搜索的：

1. **区间扫描。** 在下限到上限之间按网格设 4 个价格，看哪里卖得更好。这是粗略定位，作用是别卡在起始价格附近。
2. **阶梯搜索（ladder）。** 从最好的那个点出发，每步 8%，每走一步都评估结果。
3. **等待。** 价格保持不动，直到累计 12 笔成交且至少满 3 天。达不到这个量，需求估计毫无意义。
4. **掉头与收敛。** 变差了就往反方向走一步。连续变差两次，就退回最好的价格，并把步长减半。

决策依据不是平均销量，而是需求的**下界估计**：数据还少的时候，引擎按悲观情形推算，不会因为三笔成交碰巧好看就扑上去。

被外部因素污染的日子——商品断货、正在做活动、广告有突增、会员折扣改动过——会被打上标记，不参与估计。

保本价下限在这里同样是硬边界：实验不能把价格带进亏损区。

五种策略类型：

| 策略 | 最大化什么 |
|---|---|
| `ref_price` | 什么也不搜——只守住基准价。默认值 |
| `max_profit` | 每天的利润 |
| `max_revenue` | 每天的营收 |
| `max_units` | 在满足目标毛利率的前提下的成交件数 |
| `liquidation` | 清货速度。唯一被允许跌破成本价的模式——跌多深由你指定 |

## 怎么核查程序做了什么

- **调价器日志** —— 每个运行批次对每个商品的决策：原价、新价、基准价、偏离、动作和原因。
- **策略决策日志** —— 实验引擎提出了什么、为什么，包括那些没有被采纳的建议。
- **驾驶舱** —— 按在险金额排序的任务。
- **价格快照** —— 每次批量写入之前的状态，可以回滚。
- **生效校验。** 下发三分钟后会从平台把价格重新读回来。如果平台回复成功却没把价格设上去，这条记录会被标为 `VERIFIED_FAIL`。这种情况比想象中常见。

---

## 程序不做什么

老实列一份清单，免得产生不该有的期待：

- **不盯竞品价格。** 这里没有页面抓取——Ozon 规则禁止这么做，责任会落到你的卖家后台头上。价格是从你自己的经济账算出来的，不是从别人的价格算出来的。
- **不核验你的成本价。** 成本价填错，就会得到一个算得很自信的错误下限，系统无从发现。
- **不自动管理广告。** 广告支出会被采集并计入 P&L，关停投放的工具也有，但它本身不管理出价。
- **不计算增值税。** 这套模型是按简易计税设计的。
